## Context

当前项目是一个面向中国大陆用户的 QQ Bot Docker 部署方案，包含三个核心服务（NapCat、AstrBot、Gsuid-Core）。项目已有基本的部署脚本和 Docker Compose 配置，但缺少生产级保障措施：

- Bash 脚本没有统一错误处理，失败时用户难以定位问题
- Docker Compose 缺少健康检查和重启策略，服务异常退出不会自动恢复
- 文档分散在多个 README 中，缺少故障排查指南
- 存在安全隐患（`safe.directory '*'`）
- Windows 开发环境下脚本可能出现行尾问题

目标用户是 Linux 服务器运维人员，通常对 Docker 有基础了解但不是专家。

## Goals / Non-Goals

**Goals:**
- 部署脚本在任何步骤失败时给出清晰的错误提示和修复建议
- Docker 服务具备自动恢复能力（重启策略 + 健康检查）
- 新用户通过文档可以独立完成部署和常见问题排查
- 脚本可重复执行（幂等性），不会因重复运行而破坏已有配置

**Non-Goals:**
- 不改变现有服务的版本或镜像来源
- 不引入新的编程语言或框架（保持纯 Bash + Docker Compose）
- 不支持 Windows 原生部署（仅 Linux/Ubuntu）
- 不实现 CI/CD 流水线
- 不修改 `role.md` 等业务配置
- 不添加服务间依赖排序（三个服务可同时启动，无需等待）

## Decisions

### 1. 统一错误处理模式：`set -euo pipefail` + trap

**选择**：在所有脚本顶部添加 `set -euo pipefail`，并用 `trap` 捕获错误输出友好信息。

**替代方案**：在每个命令后手动检查返回值 — 过于冗长且容易遗漏。

**理由**：`set -euo pipefail` 提供全局兜底，`trap` 在失败时输出出错行号和脚本名，用户可以快速定位问题。

### 2. 日志系统：彩色 printf 函数

**选择**：定义 `log_info`/`log_warn`/`log_error`/`log_step` 函数，使用 ANSI 颜色码。

**替代方案**：使用 `echo` 直接输出 — 无法区分信息级别，在大量输出中难以定位警告和错误。

**理由**：彩色日志在终端中视觉区分度高，且函数化后可统一添加时间戳或日志级别前缀。

### 3. 健康检查策略

**选择**：
- NapCat：HTTP 检查 6099 端口（`/api/get_login` 端点）
- AstrBot：HTTP 检查 6185 端口（根路径）
- Gsuid-Core：HTTP 检查 8765 端口

**替代方案**：TCP 检查 — 只能验证端口监听，不能确认服务实际可用。

**理由**：HTTP 健康检查能验证服务已完整启动，而非仅端口绑定。设置合理的 `start_period` 避免启动期间的误判。

### 4. 重启策略：`unless-stopped`

**选择**：所有服务使用 `restart: unless-stopped`。

**替代方案**：`always` — Docker 升级后也会自动重启，即使之前被手动停止。

**理由**：`unless-stopped` 在手动停止后不会自动重启，符合运维预期，同时在异常退出时自动恢复。

### 5. 镜像修复整合为可选步骤

**选择**：在 `run_napcat.sh` 中添加 `--fix-mirror` 参数，将镜像修复逻辑内联，保留 `fix_docker_mirror.sh` 作为独立工具。

**替代方案**：合并两个脚本为一个 — 某些用户可能只需修复镜像而不重新部署。

**理由**：提供统一入口的同时保留灵活性，`--fix-mirror` 标志让一键部署用户可以顺便修复镜像问题。

### 6. Git safe.directory 精细化

**选择**：仅对 `gsuid_core` 仓库目录设置 `safe.directory`，而非 `*`。

**替代方案**：完全不设置 — Docker 容器内 uid 映射会导致 git 操作失败。

**理由**：`*` 通配符允许任何目录的 git 仓库跳过所有权检查，存在安全隐患。仅针对需要的仓库设置既解决问题又缩小攻击面。

## Risks / Trade-offs

- **健康检查端点可能变化** → 使用宽松的超时和重试次数，并添加注释说明端点来源
- **彩色日志在不支持 ANSI 的终端上显示乱码** → 检测 `TERM` 环境变量，非交互终端自动降级为无色输出
- **`set -e` 可能导致某些预期内的命令失败退出** → 对预期可能失败的命令使用 `|| true` 或 `if` 判断
- **增加脚本复杂度** → 保持函数化但避免过度封装，每个函数职责单一
